## 1. 产品现状评估

### 已经做对的

| 维度           | 评价                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| **核心链路**   | URL 拦截 → 规则匹配 → 分发，闭环完整且工作正常                                |
| **架构选型**   | 单 App + Carbon Apple Event 直收，比业界常见的 AppleScript 转发器方案干净得多 |
| **匹配引擎**   | 6 种模式 + 优先级 + www 归一化，能力已超过 Velja / Browserosaurus 等同类      |
| **多账户支持** | Chromium `Local State` + Firefox `profiles.ini` 双路检测，是明显的差异化亮点  |
| **代码注释**   | `_darwin.go` 系列的注释质量很高，把「为什么不能用更显然的写法」都记录下来了   |
| **卸载还原**   | 记录并还原安装前的默认浏览器，比很多同类工具（直接甩给 Safari）体贴           |

### 主要差距

| 维度                 | 差距                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **规则可编辑性**     | 只能增删，不能改、不能禁用、不能调优先级——这是最伤日常使用的短板                                                          |
| **国际化实际生效性** | 7 个语言包；安装后跟随系统区域语言（[ISSUES I-4](ISSUES.md#i-4--安装后-gui-始终以英文启动系统语言检测在-app-场景下必然失效已解决) 已解决） |
| **分发能力**         | 无公证签名、无 Homebrew Cask、无自动更新，只能"自己 clone 自己编译"                                                       |
| **反馈可见性**       | 规则命中/未命中、URL 被丢弃、profile 检测失败，全部无提示                                                                 |
| **测试有效性**       | 决策逻辑的测试测的是复制品（[ISSUES I-1](ISSUES.md#i-1--url-决策逻辑存在三份副本且测试测的是副本而非生产代码)）           |

### 竞品定位

| 产品                                | 定位                          | Browser Switch 的差异                           |
| ----------------------------------- | ----------------------------- | ----------------------------------------------- |
| **Velja**（免费/内购）              | 规则 + 深链接分流，生态最成熟 | 我们有多账户 profile，它没有                    |
| **Browserosaurus**（开源/Electron） | 纯选择器，无规则引擎          | 我们有完整规则引擎，且是原生二进制（它 ~150MB） |
| **Finicky**（开源/JS 配置）         | 极强，但要写 JS 配置文件      | 我们有 GUI，面向不写代码的用户                  |
| **Choosy**（付费）                  | 老牌，规则 + 选择器           | 我们免费开源                                    |

**结论**：产品的独特生态位是 **「Finicky 的规则能力 + Browserosaurus 的 GUI 易用性 + 谁都没有的多账户分流」**。应该把资源压在**多账户 profile 分流**这个差异点上，而不是去补齐一堆通用功能。

### v1.2 —— 规则系统的可用性补完（建议 3~4 周）

**目标**：让规则真正"可管理"，而不是"只能重来一遍"。

#### 2.1 规则编辑器重做

- 规则行支持**点击编辑**（复用 `showAddRuleDialog` 表单，传入已有 `Rule`）
- 每行加 **Enabled 开关**（引擎早已支持，只差 UI）
- 显示**优先级数值**与**来源徽章**（`auto` 记住选择 / `user` 手动创建）
- 支持**拖拽排序** = 调整优先级（比让用户填数字直观得多）
- 手动规则默认优先级 `100`，自动规则降为 `50`（I-10：显式配置应优于隐式记忆）
- 新增规则时检测同 pattern 冲突，提示「已存在规则 X → 浏览器 Y，是否替换？」

#### 2.2 规则调试器

把 `--test` 的能力搬进 GUI：设置界面加一个输入框，粘贴 URL 后实时显示：

```
https://mail.google.com/u/1/inbox
  ✗ *.company.com       (wildcard, priority 100)  未命中
  ✓ *.google.com        (wildcard, priority 90)   命中 → Google Chrome
    → 将用 Google Chrome 打开
```

这是同类产品普遍缺失的能力，成本极低（`MatchURL` 已有 `MatchLog`），对"规则写不对"的用户价值极大。**顺带把 `MatchLog` 国际化**（I-27）。

#### 2.3 规则导入 / 导出

单个 JSON 文件导出规则集，方便在多台机器间同步、方便社区分享规则模板（如「前端开发者规则包」「多租户运维规则包」）。

### v1.3 —— 押注差异点：多账户分流（建议 4~6 周）

这是产品唯一的护城河，应该做深。

#### 3.1 规则支持指定 profile（最高价值）

当前 `Rule` 只有 `Browser` 字段，「记住选择」也明确不记 profile（PRD F8）。而多账户用户的真实诉求恰恰是：

> `*.company.com` → Chrome 的**工作账户**
> `*.personal.com` → Chrome 的**个人账户**

**改造**：`Rule` 增加 `Profile string` 字段（空 = 默认 profile），`MatchURL` 返回 `*Profile`，命中时走 `LaunchBrowserProfile()`。「记住选择」在账户菜单里选定后连 profile 一起记。

向后兼容：老配置无 `profile` 字段，JSON 反序列化为空串，行为不变。

**这一条的价值超过本文档其余所有功能之和。** Velja、Choosy、Finicky 都做不到「同一浏览器不同账户分流」。

#### 3.2 账号（profile）可独立收藏 —— ✅ 已实现（2026-07-08，方案 A）

**来源**：用户实测反馈（2026-07-08）。设置界面展开 Chrome 后能看到「用户1 / 无痕」三个账号，但它们是**只读**的——无法像浏览器那样点 ♥ 收藏。

**已交付**：采用方案 A（复合字符串 key）落地。`Favorites` 中 `bundleID` 表示整浏览器，`bundleID#profileID` 表示指定账户；新增 `FavoriteItem` 类型与 `FavoriteItems()`，`FavoriteBrowsers()` 降为兼容包装。设置右侧展开的每个账户（含无痕）可点 ♥ 收藏，选择器中账户收藏项作为独立卡片（标题「浏览器 · 账户」）直接打开并占用独立 ⌘N 编号。悬空项（浏览器卸载 / 账户删除）自动跳过。单元测试见 [favorites_test.go](../favorites_test.go)。以下为当时的设计记录，供回溯。

**诉求**：在多账号浏览器下，**每个账号都应能独立收藏**，收藏后作为选择器里的独立卡片出现，并获得自己的 ⌘N 编号。典型场景：

> 收藏「Chrome · 工作账户」和「Edge · 个人账户」两张卡片，
> 点击/⌘1 直接用工作账户开 Chrome，无需先点浏览器再从菜单里选账户。

**这是 3.1 的对偶**：3.1 让**规则**能指定账户（自动分流），3.2 让**手动收藏**能指定账户（手动快捷入口）。两者共享同一套 profile 启动逻辑，应在同一版本一起做。

##### 数据模型改造（核心，影响面最大）

当前 `Favorites []string` 只能存浏览器 ID，无法表达「某浏览器的某账户」。三种候选方案：

| 方案                      | 形态                                                              | 优点                                                                                   | 缺点                                                                                       |
| ------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **A. 复合字符串**（推荐） | `favorites: ["com.google.Chrome", "com.google.Chrome#Profile 1"]` | 改动最小，`Favorites` 仍是 `[]string`；无 `#` 即整浏览器，有 `#<profileID>` 即指定账户 | 需要一个解析约定，profileID 含特殊字符时要转义                                             |
| **B. 结构化数组**         | `favorites: [{browser, profile}]`                                 | 语义最清晰                                                                             | JSON schema 破坏性变更，需迁移旧配置（旧的 `["id"]` 字符串数组无法直接反序列化为对象数组） |
| **C. 并列新字段**         | 保留 `favorites`，新增 `favorite_profiles: [{browser, profile}]`  | 完全向后兼容，旧字段不动                                                               | 两个字段各存一半，排序（决定 ⌘N 编号）需要合并两个列表，顺序管理复杂                       |

**倾向方案 A**：向后兼容最好（旧配置的纯 bundleID 天然是"无 `#`"的合法值），且 `Favorites` 保持 `[]string` 不破坏排序/上下移逻辑。约定：

```
收藏项 key = bundleID                    → 整浏览器（默认 profile）
收藏项 key = bundleID + "#" + profileID  → 指定账户
```

`FavoriteBrowsers() []Browser` 需升级为返回一个新类型，例如：

```go
// FavoriteItem 表示一个可收藏单元：整浏览器，或浏览器的某个账户。
type FavoriteItem struct {
    Browser Browser
    Profile *Profile // nil = 默认 profile / 整浏览器
}
func (c *Config) FavoriteItems() []FavoriteItem
```

##### 边界与决策点（实现前需明确）

1. **无痕能否收藏？** 截图里「无痕」也是一行。无痕是合成 profile（`ID="__incognito__"`），可以收藏，但「记住选择」等逻辑要排除它。建议：允许收藏，key 为 `bundleID#__incognito__`。
2. **账户被删除后的收藏项**：用户在 Chrome 里删了某 profile，收藏 key 变成悬空引用。`FavoriteItems()` 应静默跳过解析不到 profile 的项（类比现有 `findBrowserByID` 返回 nil 即跳过）。
3. **⌘N 上限**：收藏浏览器 + 收藏账户混在一起可能超过 9 个，⌘N 只覆盖前 9，需和「更多」折叠逻辑对齐。
4. **卡片标题空间**：「Google Chrome · 工作账户」较长，需复用 `shortName()` 并对 profile 名截断。
5. **与 3.1 的一致性**：3.1 的 `Rule.Profile` 用 profileID 存储，3.2 的收藏 key 也用 profileID，两者应共用同一套「profileID ↔ Profile」解析，避免两套 ID 体系。

##### 验收

- 设置里展开任一多账号浏览器，每个账户（含无痕）行尾有可点的 ♥
- 收藏「Chrome · 工作」后，选择器出现独立卡片，标题含账户名，⌘N 编号连续
- 点击该卡片 / 按对应 ⌘N，直接用该账户打开 URL（走 `LaunchBrowserProfile`），不弹二级菜单
- 删除该 Chrome profile 后重新扫描，悬空收藏项自动消失，不报错
- 旧版 `config.json`（`favorites` 为纯 bundleID 数组）加载后行为完全不变

> **工作量预估**：数据模型 + 4 文件联改 + 边界处理，约 2~3 天。风险集中在 `Favorites` 语义扩展对现有排序/隐藏逻辑的回归，需补充针对 `FavoriteItems()` 的单元测试。

#### 3.3 profile 显示优化

- 修复 Firefox 默认 profile 识别（I-8）
- 账户菜单显示 profile 的头像（Chromium 的 `Local State` 里有 `avatar_icon` 字段）与关联邮箱（`user_name`）
- 选择器卡片右下角加小角标，直观提示「此浏览器有 3 个账户」
- 统一左键点击与 ⌘N 的语义（I-9）：卡片主体直接打开默认 profile，右下角「▾」区域展开账户菜单

#### 3.4 无痕模式提升为一等公民

当前无痕只是账户菜单里的一项。建议：

- 选择器加一个全局「本次用无痕打开」开关（`⌘⇧N`），勾选后点任何卡片都走无痕
- 规则支持 `incognito: true`，实现「所有 `*.ad-tracker.com` 一律无痕打开」

## 3. 明确不做的事（Non-Goals）

写下来是为了抵抗特性蔓延：

1. **不做浏览器扩展**。产品价值在系统层拦截，做扩展就退化成书签管理器。
2. **不做云同步 / 账号体系**。规则导出为 JSON 文件，用户自己丢进 iCloud / Dropbox 即可。引入账号会带来隐私争议与运维成本，与工具定位不符。
3. **不做规则的脚本化 DSL**。那是 Finicky 的位置。本产品的用户画像是"不想写 JS 的人"。若真需要脚本，导出 JSON 让用户外部处理。
4. **不做跨平台**，除非有明确用户需求（见上表）。
5. **不做 URL 内容嗅探**。不发起任何用户未主动触发的网络请求（短链展开若做，必须显式开关 + 明确告知）。
